# 0001. 全局命名空间脚本而非模块打包

- 状态：已接受
- 日期：2026-09-21

## 背景与问题

扩展包含十来个互相协作的脚本（数据层、提取、简历解析、表单填写、LLM 通道、后台编排），需要决定代码组织方式。MV3 service worker 支持 ESM，但 content script 与 popup/options 页的模块支持各不相同，且本项目刻意不引入任何构建工具。

## 决策

不用 ESM、不打包。每个 `.js` 是一个 IIFE，把公开对象挂到 `globalThis` 的命名空间上（`BossJdDB`、`BossJdExtract`、`BossJdResumeText`、`BossJdFill`、`BossJdLlm`、`BossJdAgent`、`BossJdCoach`），靠三处加载顺序协作：

- 各 HTML 底部的 `<script src>` 顺序（popup/options/favorites/coach 及 tests 夹具）；
- `background.js` 顶部的一行 `importScripts("db.js", "llm.js", "agent.js", "coach-agent.js")`；
- manifest `content_scripts` 的 `js` 数组顺序（`extract.js, resume-text.js, fill.js, content.js`）。

## 理由

- 保持「无构建、无 npm 依赖」：加载即用，浏览器直接跑源码，调试时看到的行号就是文件本身。
- 三种上下文（页面、扩展页、service worker）用同一套 IIFE 模式，不需要为 ESM 在不同入口做差异化包装。
- 代价（依赖加载顺序、命名冲突靠约定避免）在本项目规模下可控，且各 HTML 的 script 列表就是显式的依赖清单。

## 影响

- 新增共享模块时必须在所有用到它的 HTML 和 `importScripts`/manifest 两处同步登记。
- `popup.js` 的兜底注入文件列表必须与 manifest 的 content_scripts 保持一致，改一处就要查另一处。
- 模块间只通过命名空间对象调用，禁止在 IIFE 之间共享未挂到 `globalThis` 的内部变量。
